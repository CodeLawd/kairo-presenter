# Managed licensing

`church_licenses` holds each church's licence, one reusable activation key, activated devices, UTC-month usage counters and expiring transcription slot reservations. Its unique `orgId` index prevents concurrent free issuance creating two licences. Device activation, device limits, monthly request reservations, and transcription slot/minute reservations each use one atomic MongoDB document update. Keys are generated from 24 random bytes, retained only as a SHA-256 hash plus an AES-sealed copy for owners/admins, and remain valid while the licence is active. Revoking clears the key without deactivating computers. An owner/admin may create a key for an existing active licence even when new free issuance is disabled. Superadmins can create or amend a licence through PATCH for a real church.

The global `licensing_config` document encrypts provider keys and the generated Ed25519 signing private key using the existing vault encryption key. The unique global-name index and insert-only initialization preserve one signing identity across concurrent processes and restarts. Provider updates use compare-and-swap to avoid lost writes. Back up the database and vault encryption key together. Customer `/secrets` reads return empty fields; writes return a migration error. Legacy encrypted church vault records are not used or migrated into the platform vault.

Authenticated online snapshots sign `UTF8(JSON.stringify(claims))` using Ed25519 and return a PEM SPKI public key and base64 signature. All claim timestamps use Unix seconds. Claims have fixed insertion order: orgId, deviceId, features, issuedAt, refreshAfter, expiresAt, licenseExpiresAt. Refresh is due daily; offline validity is at most 14 days and clipped to licence expiry. Offline clients must pin the signing key through authenticated online activation/refresh, verify signatures, bind org/device, check expiry, and reject clock rollback. Revocation and feature changes take effect immediately for online managed requests; an already issued offline lease remains usable until expiry.

Provider HTTP origins and paths are fixed allowlists. JSON request bodies, accepted fields, inexpensive model names, output tokens, message counts, search result counts, and translation characters are bounded. LLM `purpose` selects scripture/summaries/translation/webSearch; it is a client-declared purpose, not content classification. Dedicated provider paths enforce their intrinsic feature. All purposes share the monthly request cap. A managed request reserves one request before contacting the provider, including failed requests. A server recap reserves two requests for draft/review per attempt, with fresh membership and church entitlement checks using the persisted generation actor. Server-owned recap jobs accept web dashboard users without requiring their browser session to occupy a presentation device slot; raw desktop managed requests always require an activated device. No upstream error body or credentials are returned to clients.

## Transcription limit

The API atomically enforces **grant/session reservations**, not an upstream hard spending limit. A grant reserves two minutes and a 90-second application slot; renewals are allowed once per 60 seconds and reserve another minute while extending the slot for 90 seconds. Failed grants release the slot but do not refund reserved minutes. Abandoned slots expire without a background cleanup job. Renew/release bind the session to its authenticated church and device. Month boundaries reset the shared counters atomically.

Deepgram's `/v1/auth/grant` issues a 30-second token. Its TTL limits connection establishment, not connection duration, and its token permits other inference APIs as well. A client could reuse the token or retain a connection beyond an application slot's expiry. Consequently stopping renewals, revoking a licence, or exhausting the application budget cannot forcibly close that provider connection, and counters record reserved time rather than provider-confirmed audio usage. For a strict cost/concurrency boundary, replace direct grants with a server-owned WebSocket audio relay that closes upstream connections at the reserved deadline, or use isolated provider projects and provider-side quotas. Do not market these application reservations as a hard billing cap.

Official reference: https://developers.deepgram.com/guides/fundamentals/token-based-authentication

`licensing_audit` records actor, action, church (when applicable), and timestamp for policy/provider/licence/key/device operations. It deliberately excludes key values, hashes, prompt/transcript content and token values.
